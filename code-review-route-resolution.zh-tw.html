為什麼 w.Gateways 會跨 namespace

程式碼註解主張候選集內不可能有同名 Gateway： 「within a resolution the candidate set can never hold two same-named Gateways (K8s per-namespace name uniqueness)」。這對候選集成立， 但 ScopedFor 掃的不是候選集，是整包已載入的 w.Gateways， 而那一包確實會跨 namespace，有兩條路徑：

  • clickhouse.go:446 的 hop-3 SQL 用 has(?, namespace) 帶入 nsList，而 nsList 是同一個 IP 底下所有 ingress Service 的 namespace 聯集（clickhouse.go:371–388）。單一 IP 就足以觸發。

F5 — ResolveRoute 外沒有 recover()（hardening，非契約違反）

本檔案先前判定更正後判定
嚴重 —— 違反「route resolution can never fail a build」， 並以 topology.go 的 recover() 作為 「其他路徑有做、這裡沒做」的對照。 次要 —— 該對照不成立（理由見下）， CLAUDE.md 的契約範圍不涵蓋 panic。仍建議加固，但不是缺陷。

為什麼先前的對照是錯的

pkg/build/topology.go:163–169 的註解把理由寫得很清楚：

// The closure recovers its own panics: errgroup (x/sync, post-#53757-revert)
// does NOT propagate goroutine panics to Wait, so an unrecovered panic here
// would kill the whole process — the HTTP recovery middleware only covers the
// handler goroutine. Converting to an error keeps the standard
// build-failure path (sanitised 500, full detail in server logs).

兩件事因此成立：

  • topology 的 recover() 存在的理由是 process-safety —— errgroup 起的是獨立 goroutine， gin 的 recovery middleware 管不到，不 recover 會殺整個 process。 它不是「降級為 external」的先例：註解自己說明 recover 之後仍然走 build 失敗路徑（500）。
  • resolveRouteQueries 是序列跑在 handler goroutine 上， gin 的 recovery 本來就接得住。panic 的後果（500）與 topology panic 的後果 完全相同。所以「其他路徑有保護、這裡沒有」是誤述。

另外，CLAUDE.md 的原文是 「any miss/error degrades to the existing external node — route resolution can NEVER fail a build」—— 契約的主詞是 miss 與 error，panic 不在其中。 routeprescan.go:283 的註解同理 （「Errors and misses are recorded in the index — never returned」）。

仍然值得做的理由

後果雖然「只是」500，但 v1 沒有 result cache —— 只要那個 key 還在被查詢，每個 /v1/graph 請求都會重跑並重新 panic， 亦即一個 endpoint 的問題會讓整個 API 持續不可用。 而這正是把 route resolution 設計成 opt-in 加值功能時想避免的情況。 加固成本極低（迴圈內包一層 defer recover() → failed: true， 走既有的 error 降級路徑），沒有行為變更風險。

觸發可能性（誠實評估）

先前版本舉的例子是「DiscardUnknown: true 產出欄位不完整的 networking.Gateway → istiod nil-deref」。 這個鏈條未經證實 —— istiod 本身就是設計來處理使用者提交的 CR， 多數路徑對缺欄位有防禦。真正的觸發點更可能是 translate.go 手工組出來的 model.Environment （ServiceDiscovery／PushContext 未經 istiod 正常初始化路徑）， 但同樣沒有實證。視為防禦性加固，不是已知的失效模式。

建議

  • 在 resolveRouteQueries 迴圈內包一層具名函式， defer recover() 後記為 routeEntry{failed: true} —— 與既有 error 處理走同一條降級路徑，不新增 outcome。
  • panic 應 log 在 Warn/Error 等級（比 error 的 Debug 高）。
  • 補測：注入會 panic 的 mock resolver，斷言 build 仍成功且該 endpoint 降級 external。
